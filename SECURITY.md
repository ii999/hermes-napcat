# Security boundaries

A QQ channel gives remote people a route to an agent. Deploy a dedicated account and Hermes profile. Start with user and group allowlists and empty toolsets; grant only the capabilities needed for your use case. A prompt, role name or administrator label is not an OS sandbox. Tools executing code need their own container/user/filesystem restrictions.

The adapter checks self_id, user authorization and group authorization before processing messages or attachments. Hermes performs a second gateway authorization pass. `NAPCAT_ALLOWED_USERS` is required for a consistent gate at both layers. `admins` enables gateway control; it does not grant model tool access or bypass upstream policy. Group sessions override model toolsets with an empty list by default.

Transport tokens go in Authorization headers, never URL query strings. Non-loopback plaintext links require operator opt-in. Use private networking or certificate-verified TLS, keep OneBot and NapCat management ports off the public Internet, and do not log authorization headers. Treat OneBot itself as a trusted service: a stolen token or compromised NapCat process can forge events for that bot account.

Inbound and outbound media have independent URL policies and HTTP sessions. Both default to the legacy exact allowlist; an explicit public mode removes only the hostname-list requirement. Both check actual connection-time DNS results and literal IPs, reject non-public addresses unless an exact private origin is trusted for that direction, validate every redirect, verify TLS certificates, ignore proxy environment settings, enforce transfer/cache bounds and refuse encoded bodies. Configure trusted_private_origins only for dedicated read-only media servers; a URL path can invoke a sensitive GET endpoint on a privileged service. Image header checks are not a full decoder sandbox. Keep media parsers patched. Local outbound file access is restricted to explicitly configured roots and resolved paths; concurrent malicious modification of the local filesystem is outside this process-level check.

Media allowlists also accept explicit `*.example.com` patterns in either direction or the inherited legacy policy. A pattern matches one or more subdomain labels, never the apex or a lookalike suffix; add the apex separately if needed. Only a leading `*.` followed by an ASCII DNS domain with at least two labels is accepted, not arbitrary globs or IP patterns. Use Punycode for internationalized suffixes. A wildcard grants access to all subdomains of its suffix, so configure only domains you trust; it does not grant private-origin trust or bypass connection-time DNS and redirect checks. The default hosts remain exact.

Sending requires the `napcat_qq` toolset and `qq_tools.enabled`. Reading requires `napcat_qq_read` and either `qq_tools.read_enabled` or the legacy `qq_tools.enabled`. The read-only switch never grants sending. Existing deployments must add the new read toolset to discover getters after upgrading. Calls bind to the current NapCat session and profile. A different target requires `allow_cross_chat`, a configured administrator, and an allowlisted destination. Media handles remain same-chat even for administrators. The plugin does not expose raw OneBot actions, `@all`, attachment URLs, arbitrary forward IDs, group administration, or Qzone operations.

Tool-provided HTTP(S) media passes through the same downloader before NapCat sees it. Tool-provided local files must stay under explicitly approved outbound/shared roots; large shared-path sends still rely on the operator to mount the mapped directory with suitable permissions. Generated merged-forward nodes always use the bot's QQ ID, though their display label and content remain model-controlled. Treat every tool result marked `partial` or `delivery_uncertain` as an instruction to inspect QQ before retrying.

Optional media references cover images, records, videos and files, retaining bounded account/chat/author/message/time/expiry metadata and internal locators. Context/tool output exposes opaque IDs and bounded display metadata. Resolution checks the current user, target and source-author visibility. Current and explicit quoted attachments share count and byte budgets (defaults: four attempts and 64 MiB); a failed transfer consumes its full allowance. Recent same-author selection is opt-in and runs only without current attachments or an explicit quote. Observation is metadata-only; proactive turns do not automatically load media. Re-observation may enrich missing locators without extending source-based expiry.

Inbound media prefers authenticated bounded WebSocket download streams. Only fixed download actions are used; each echo has count/buffer limits, chunks require canonical base64 and contiguous indices, and actual bytes and completion totals must match. Converted record metadata can describe original bytes, so the actual MP3 payload is bounded independently. Socket epoch, access and recall checks apply during and after transfer. Completed data is published atomically into exclusive 0600 UUID cache files; failures remove partial files. Remote filenames supply only approved suffix hints, never local paths.

In `auto` mode, HTTP fallback is permitted only for an explicit unsupported action (failed/1404/normal-action before data), a missing safe opaque ID, or explicit file unavailability after one verified same-message locator refresh. Malformed streams, resource violations, authorization failures, timeout and disconnect do not trigger fallback. Strict `stream` mode never falls back. Both permitted `auto` HTTP fallback and explicit `http` retain DNS/redirect/origin restrictions and may refresh a stale 403/404/410 locator through the verified original message. All stale-locator paths share a maximum of one refresh; provenance and expiry never change.

Private history rows prove the target/account, author, time window and recall state independently; bot authorship alone does not prove a private destination. Forward reads derive IDs from a verified, visible parent message and share depth/node/UTF-8-byte budgets. Claimed forward-node authors are attribution, not authorized principals; media access and expiry follow the verified parent. File notices require the same ACL, shape, time and byte checks, and their generated IDs cannot authorize message/history queries. Notice/message dedup is bounded by conversation, author and exact file locator; different opaque and URL locators cannot reliably be equated.

`qq_read_media` resolves through the gateway and invokes installed Hermes handlers in the requesting profile/task context. Native vision envelopes are preserved; transcription respects runner STT enablement and only uses an installed local fallback. Video and document handlers must be available. Document results default to 200 lines (maximum 500) and ordinary strings are capped at 16,000 characters, but extraction may parse the entire bounded document. Returned content and native image inputs remain untrusted model input. Parsing/decoding requires its own OS resource and isolation controls.

Recall checks run before/after awaited reads and inside the send gate. Missing recall notifications cannot be reconstructed reliably, and the plugin cannot retract already delivered model inputs, tool paths or QQ messages. A returned local path can be consumed by separately authorized filesystem/vision tools: scoped references are not an OS sandbox against those tools. Incoming local paths and inline payloads are not accepted as get_image IDs or opened as local files.

A dedicated shared_cache_dir can stage validated URL/local/cached media without exposing the whole inbound cache. Received media lives under the profile's standard document-cache parent, resolved by `get_hermes_dir('cache/documents', 'document_cache')`, in a plugin-owned `napcat` subdirectory. Hermes's agent-visible path mapping does not prove a live sandbox has synchronized newly downloaded bytes. Download and staging share quota; copies consume additional space. Only expired plugin-named regular files are pruned during later I/O, not immediately at TTL expiry. Use per-profile storage, compatible process identities/ACLs, and read-only NapCat mounts. Do not grant untrusted local users write access.

Host-driven standalone forward delivery accepts bounded local-path/voice pairs and preflights every input before the first QQ message. It uses the same outbound roots, preparation, quota and epoch checks as the gateway; it cannot borrow incoming same-chat media handles without a requester context. `force_document` selects file delivery. Reverse mode requires a live gateway. Compound delivery may complete only a prefix; preserve returned IDs and inspect QQ before retrying. Existing-message merged-forward nodes provide server-side resend after provenance checks; raw single-message forwarding with ambiguous null IDs is not exposed.

Recent-ID deduplication and queues live in process memory. A crash, overload or OneBot disconnect can lose events. The plugin does not guarantee exactly-once delivery. If a message action times out after a write, inspect the QQ conversation before retrying. Partial sends expose known message IDs; never treat a successful prefix as full delivery.

QQ participants can supply prompt injections through text, quotes, images and documents. The plugin preserves source identity and limits gateway control but cannot guarantee model-level instruction isolation. Review the full Hermes tool and memory configuration before sharing a group session.

Report a vulnerability privately to the repository owner. Do not include working tokens, complete private message histories or personal account details in a public issue. The source release has not undergone an independent security audit or a live QQ acceptance test.

Explicit outbound base64/data URIs are length-checked before decoding and tool-key serialization, then decoded in bounded blocks with strict canonical encoding and image MIME/header checks. Small validated inline payloads need no disk copy; larger imports use the existing cache quota. This does not enable inbound base64/path fallbacks.

NapCat stream uploads use operator-bounded size/concurrency/timeouts, random IDs and filenames, per-chunk acknowledgements, and end-to-end SHA-256/size checks. A stream path is accepted only for the generated filename and original connection epoch, never opened locally or returned as arbitrary filesystem authority. Queued sends recheck retention and connection identity. No upload/send replay follows timeout or uncertain acknowledgement. Cleanup attempts only reset the current random stream; reset errors are not proof of deletion and remote retention remains necessary. NapCat's inspected implementation buffers the final file in memory, so chunking does not guarantee bounded remote memory independent of file size.

The increased WS default is paired with a 64 MiB serialized-event byte budget including active handlers and a separately bounded recall lane. This is a protocol budget, not an exact Python heap or decoder memory limit. Keep process/container resource limits in production.
